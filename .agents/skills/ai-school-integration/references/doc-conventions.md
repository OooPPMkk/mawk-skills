# 文档写法与收口口径

三份主文档各有唯一职责，**不要互相复述**：批次状态在 plan，批次明细与决策在 history，缺陷与登记需求在 issues-v3。

## plan：`ai-school/doc/ai-school-integration-plan.md`

- 头部固定块：流程指针（指向本技能）/ 新会话接续 / 底线（后端仓与 harness 仓边界）/ 基线与分支口径 / 权威文档。基线 SHA、分支口径、接口基址随变化更新。
- §1 当前状态：当前批次（一句 + 指向历史文件）、**最近一轮**对账结论（日期 + 定性 + 指向 `Dn`）、历史对账压成一行指针、共享层回提、「后续动作」。写完一批就刷新；**不复述 SHA 明细与逐条对账内容**。
- §2 批次计划：`待开始` / `挂起` / `已完成` 三段。每个待开始批次写 **范围 / 口径 / 依赖** 三项；挂起批次必须写清卡在哪个契约（如 v3 `WS-1` / `WS-2`）。已完成段只留一行指向 history。
- §3 决策记录：不放内容，只一行指向 history。
- §5 流程与规范：**只留一行指针指向本技能**，不写内容（流程与规范的权威源是技能）。
- §6 前端动作台账：**只留未闭环项**，格式 `现状 → 后端交付后的联动动作`；项闭环即删（如 `P2-4` 闭环后删除）。

**维护顺序（推进一批时）**：先更新 §2 批次范围与口径 → 口径或决策变化记 history `Dn` → 缺陷与需求记 harness v3 → 收尾刷新 §1 与 §6。**本文件不复述缺陷明细与流程。**

## history：`ai-school/doc/ai-school-integration-history.md`

- §1 完成批次明细，一条 `### B<n> 批次名（<SHA>）` 只写：**范围 / 口径 / 实现 / 验收 / 验证边界 / 依赖**，验收里放关键实测数据（端点、字段、数值、页面结果）。
- 只记高价值信息：**能回答「当时为什么这么定、怎么验的」**。逐文件罗列改动、diff 级细节、代码片段一律不写（要看直接读源码）。
- 批次收尾时把 plan §2 的内容搬过来并补上实现与验收，不要在两处各写一半。
- §2 决策记录：`### D<n> 决策名（日期）`，条目是**结论 + 理由 + 影响范围**，编号连续续编、永不重用。新增决策一律记这里，plan 不再维护决策表。

## issues-v3：`后端联调文档/ai-school-integration-issues-v3.md`

- 前端→后端方向，append-only；v1 / v2 已冻结，**新问题只进 v3**。
- 编号：课程域沿用 `COURSE-*`；报表 `RPT-*`、工具目录 `SHELF-*`、账务合同 `BILL-*`、对话流式 `CHAT-*`、工作台导师 `TUTOR-*`、工作台生成 `WS-*`，各自从 1 起编。编号一经使用不重用。
- **首版收口**：已闭环项不进本文件、编号跳号属正常；尚未被后端读取时按首版对待，不留迭代痕迹（不写「原方案 / 已改为」）。
- 缺陷条目段结构：`## [ID] 一句话标题` + `VERIFIED_IN_SOURCE`（源码出处）→ `EVIDENCE`（实测请求响应）→ `EXPECTED`（期望，可给二选一）→ `ACCEPTANCE`（验收判据）→ `FRONTEND_INTERIM`（前端临时实现口径）。
- 登记需求（非缺陷）用 `REGISTERED_REQUIREMENT` 段，不计入缺陷集与 `open_issue_count`。
- 收尾时同步维护：`ISSUE_INDEX` JSON、frontmatter 的 `open_issue_count` / 缺陷集列表、`REVISION_LOG`（用 `recorded_requirements_added` 之类字段记登记项）。
- 坑：表格单元格里不要出现裸 `|`（含行内代码内），GFM 会按分隔符拆列、Prettier 顺着错误拆法重排且 check 仍通过；用 `/` 或转义。

## 精简口径（用户要求「文档太啰嗦」时）

1. 删过程性叙述（「先…后来…」「曾经考虑…」），只留结论。
2. 删与其它文档重复的内容（plan 不重述缺陷明细，history 不重述流程）。
3. 删逐文件 / 逐字段的实现清单，改为一句话口径 + 关键实测数据。
4. 保留：批次号、`Dn` 编号、SHA、端点与字段名、验收结论、依赖关系、验证边界。
5. 精简要**整类一起改**，不要只改一处留下不一致的口径。
