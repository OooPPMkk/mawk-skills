# 独立设计原则

参考材料的**唯一**用途是理解契约与产品目标。本仓代码一律按 `ai-school/AGENTS.md` 与既有同类页面独立设计。

> 后端在 `bt/*` 分支上做前端改动是为了联调后端接口，不以前端规范与 UI 质量为目标：命名、组件拆分、样式数值、文案措辞、工程结构都不具备参考价值。**把它们当成「后端想表达什么」的说明书，不要当成实现蓝图。**

## 参考内容使用原则（原文，2026-10-16 起）

> 后端在 `bt/*` 分支提交的前端实现是**契约理解的参考**，不是照搬对象——① 独立设计与实现，不直接抄袭参考代码；② 先理解参考的设计思路与实现方式，再结合本仓现状与规范优化改进；③ 主动扩大参考范围（后端服务源码 / SQL 与 dev 实测对照，不只依赖 bt 分支前端 diff）；④ 实现中遇到问题即时与需求方讨论确认。

本节自 `ai-school/doc/ai-school-integration-plan.md` §5 原文迁入，口径不变；后续修订以本文件为准。

## 三类参考，各自取什么

| 参考 | 取其 | 不取其 |
| --- | --- | --- |
| 后端 Java 源码 / SQL 迁移 / dev 实测 | 端点与参数、字段名与类型、枚举取值、空值与异常边界、鉴权与错误码（**契约权威源**） | —— |
| `bt/*` 分支的前端实现 | 后端联调时预期的交互意图、字段消费顺序、边界与失败处理的口径 | 命名与文件组织、组件拆分、状态管理方式、样式值与配色、文案措辞、mock 与调试代码、注释 |
| 产品原型（`doc/prototype/`） | 页面要达成的功能目标与信息项 | 视觉细节、间距数值、编造的内容（虚构电话 / 无真实数据的入口）；不合理处先优化再与用户讨论 |

## 顺序：先理解参考，再结合本仓改进

1. 先读 `bt/*` 的前端实现与原型，看懂**设计思路与实现方式**：它想让用户看到什么、字段按什么顺序消费、边界与失败怎么处理。
2. 契约另算：以后端 **Java 源码 / SQL / dev 实测**为准。参考是实现，不是契约；两者不一致时先与用户确认。
3. 理解之后结合本仓现状与 `AGENTS.md` 规范**重写**：命名、组件拆分、状态管理、样式值、文案一律按本仓与既有同类页面决定，参考的具体写法不作为依据。
4. 差异写进参考对照表交用户核对。

顺序本身不是问题，**照搬写法才是**：读得多、写的时候仍按本仓规范落笔，就没问题。反过来若把参考当模板逐行改写，禁止信号里的问题会立刻暴露。

## 冲突处理顺序

**本仓 `AGENTS.md` 规范 > 需求与原型的设计目标 > 后端 `bt/*` 实现**

出现冲突时：先说明问题与替代方案，经用户确认后再实施；不要因为「参考里就是这么写的」而放宽本仓规范。

## 禁止信号（交付前自查）

命中任一条即说明在照搬，先自行修正：

- 文件 / 组件 / 函数 / 变量命名与参考雷同，且不符合本仓命名习惯（页面主文件具名 PascalCase、类型收口到 `src/types/`、service 只封装协议）。
- 样式里出现参考中的具体色值、圆角、间距数值，而不是 Ant Token（`theme.useToken()`）/ `--palette-*` / `rem` 规范。
- 组件结构与参考一一对应，没有考虑本仓既有同类页面的组织方式与复用边界。
- 引入了本仓没有的依赖，或用了原生能力 / 既有依赖已覆盖的库。
- 文案直接照抄，或带上了本仓禁用的写法（「·」拼接并列信息）。
- 只在参考涉及的那一处实现，没有检查同页 / 同链路其它入口是否需要一致处理。
- 参考里的 mock、调试开关、临时兜底被一并带进本仓代码。

## 自问（交付前过一遍）

1. 你能说清参考的设计思路（它为什么这么做、字段为什么这个顺序）吗？还是只记住了它的写法？
2. 命名与文件放置是否与本仓同类页面一致？
3. 样式值是否全部来自 Token / 调色板 / `rem` 规范，而不是参考里的数值？
4. 超过参考范围的地方（边界、失败处理、同页其它入口、共享层）我是否推演过并检查了一致性？
5. 参考里的 mock、调试开关、临时兜底有没有被一起带进来？
